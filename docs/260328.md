# 2026-03-28 冒烟测试总结与建议

## 其他策略的测试结果（DP, SmolVLA, XVLA）

在 LeRobot 框架下进行了除 ACT 外的其他原生策略的泛化冒烟测试，结果如下：

### 1. `smolvla` 和 `xvla`
这两个属于大型 VLA (Vision-Language-Action) 模型，在初始化策略时依赖 Hugging Face 的核心库来加载预训练模型。
* **结论**：**测试失败**。报错为 `ModuleNotFoundError: No module named 'transformers'`。
* **原因**：当前的 `evo-rl` conda 隔离环境中并未安装 `transformers` 库，如果在这个环境下直接跑这类模型，必须要在环境中加入对应依赖（例如使用 `pip install transformers` 或 `uv pip install ...`）。

### 2. `diffusion` (Diffusion Policy)
在对 `agent_pos` 进行了与 ACT 同样（在 Processor 中强行映射为 `observation.state`）的修复后，DP 的模块和网络初始化已经能跑通，但是：
* **结论**：**在计算 Loss 的前向传播时截断报错**。报错为 `AssertionError: assert n_obs_steps == self.config.n_obs_steps`。
* **原因**：Diffusion 策略默认需要一段历史时序窗口（`n_obs_steps=2`）的输入。但在 LeRobot v3.0 框架下，历史帧数据的提取在 `make_dataset` 时深度绑定了 `delta_timestamps`。因为我们在底层只是强制把旧字段名 `agent_pos` 临时伪装成了 `observation.state`，导致 Loader 根本不知道 `agent_pos` 这个字段也需要沿着时间轴展开，送进网络的特征没有时间维度，导致了 Tensor Shape Mismatch 的 AssertionError。

## 终极建议：在数据集源头转换键名
虽然通过“打补丁”骗过了不强依赖时序推断的 ACT 策略，但对于依赖时序窗口的 Diffusion Policy 等，临时重命名的方式非常脆弱且会打断 LeRobot 的特征提取管线。
如果要让 **所有原生策略（DP, VLA 等）** 都能在我们的 `v2.1 -> v3.0` 数据集上完美运作，最好的方式是：**直接写一个脚本，将你已转换好的 v3.0 数据集中的 parquet 与 info 里的底层列名全部一次性改为 `observation.state`**。

### Parquet 和 JSON 键名清洗脚本

此脚本已被验证可完美将 `v2.1 -> v3.0` 数据集中由于各种原因遗留的 `"agent_pos"` 一劳永逸地原地转为 `"observation.state"`。

```python
import pandas as pd
import json
from pathlib import Path

# 替换为你的具体数据集绝对路径
dataset_root = Path("/data/vepfs/users/intern/lingyue.yang/Evo-RL-Piper/tmp/pipeline_ab/lerobot_v21_split_A5/A")

# 1. 修改 info.json
info_path = dataset_root / "meta" / "info.json"
if info_path.exists():
    with open(info_path, "r") as f:
        info = json.load(f)
    if "agent_pos" in info["features"]:
        info["features"]["observation.state"] = info["features"].pop("agent_pos")
        with open(info_path, "w") as f:
            json.dump(info, f, indent=4)
        print("info.json modified.")

# 2. 修改 stats.json
stats_path = dataset_root / "meta" / "stats.json"
if stats_path.exists():
    with open(stats_path, "r") as f:
        stats = json.load(f)
    if "agent_pos" in stats:
        stats["observation.state"] = stats.pop("agent_pos")
        with open(stats_path, "w") as f:
            json.dump(stats, f, indent=4)
        print("stats.json modified.")

# 3. 修改所有 Parquet 文件中的列名（递归包括 data 块和 episodes 元数据）
for pq_file in dataset_root.rglob("*.parquet"):
    df = pd.read_parquet(pq_file)
    renames = {col: col.replace("agent_pos", "observation.state") 
               for col in df.columns if "agent_pos" in col}
    
    if renames:
        df.rename(columns=renames, inplace=True)
        df.to_parquet(pq_file)
        print(f"{pq_file.name} modified.")
```
*(一旦执行该脚本，LeRobot 即认为它是原生符合规范的数据无需做任何源码补丁，所有时序 Loader 和特征 Normalize 均可自动完成。)*

## 使用 `uv` 隔离运行 `smolvla` 和 `xvla`


因为在 `Evo-RL-Piper/pyproject.toml` 中，LeRobot 原生已经配置好了 `[tool.uv]` 的依赖和冲突组合，你其实**完全不需要去破坏你现有的 `evo-rl` 核心 conda 环境**。你可以随时通过一行带有 `uv run` 的命令，让它动态且无痕地拉起含有 `transformers`、`safetensors` 等特有依赖的虚拟沙盒来跑某个特定策略！

### 方法 1：使用 `uv run --extra`
直接使用你的系统层级 `uv`，告诉它带着 `smolvla` / `xvla` 下定义的 `extras` 运行 `lerobot_train.py`：

```bash
# 自动创建包含 smolvla 所需依赖 (transformers, safetensors 等) 的沙盒并在里面跑
export HF_ENDPOINT=https://hf-mirror.com
export CUDA_VISIBLE_DEVICES=0
export PYTHONPATH=src

# 注意 --extra 后面写 smolvla 或 xvla
uv run --extra smolvla python src/lerobot/scripts/lerobot_train.py \
  --dataset.repo_id=pipeline_ab/A \
  --dataset.root=/绝对路径/去/已彻底转换命名好的/数据集/A \
  --policy.type=smolvla \
  --steps=1000 \
  ...其它的训练参数...
```

### 方法 2：使用 `uv pip` 安装到当前 Conda 环境
如果就是想把你当前的 `evo-rl` conda 环境“转正”成全能环境（可能引发以后偶尔的版本冲突，特别是 `openpi` 的自定义 `transformers` 分支容易打架）：

```bash
# 进入 Evo-RL-Piper 根目录
uv pip install -e ".[smolvla,xvla]"
```
这样不仅极大加速了装包速度，还能秒级并发表搞定依赖约束。之后就像往常一样执行 `python src/lerobot/scripts/lerobot_train.py` 即可。

## 深度补丁 (Depth Patch) 逻辑链路分析

### ✅ 已连通的正确逻辑（数据集与离线处理）
1. **Types & Configs:** `configs/types.py` 中的 `FeatureType.DEPTH` 以及 `configs/policies.py` 的 `depth_features` 属性清晰分离了深度模态。
2. **Dataset Processing:** `datasets/utils.py` 正确利用后缀命名与 `uint16` 区分了深度图。在 `compute_stats.py` 中，针对 `uint16` 的特殊采样（`sample_depth`）避免了 `/ 255.0`，完全符合真实物理深度的统计提取需要。
3. **Normalization (V3 processor pipeline):** `processor/migrate_policy_normalization.py` 正确识别 `DEPTH` 类型并分配 `NormalizationMode.MIN_MAX`。
4. **Env/Inference Basics (V2-style):** `policies/utils.py` 中推理时正确处理了深度形状并未做 `/ 255.0` 操作。

---

### ❌ 缺失或断裂的逻辑（亟需修复的部分）

#### 1. 原生策略模型完全无视了深度输入 (`modeling_act.py`, `modeling_diffusion.py` 等)
目前原生的 LeRobot 策略在构造网络 Backbone（如 `ACTRgbEncoder` 和 `DiffusionRgbEncoder`）时，**仅遍历并使用了 `self.config.image_features`**。
* **问题：** 模型**完全没有读取**你新增的 `self.config.depth_features`。数据集虽然处理好了深度张量，但前向传播时模型根本没有接收它的网络分支。
* **解决方案（参考 `kuavo_train` 仓库封装）：** 必须在策略模型中显式添加或实例化 `DiffusionDepthEncoder`（或适配 `in_channels=1` 的 ResNet）。并且在 `forward` 和 `_prepare_global_conditioning` 阶段，将 `observation.depth.xxx` 压成单通道提取后，与 `global_cond` 或 Transformer 的视觉 Token 拼接融合。

#### 2. V3 观测数据预处理管线的暴雷隐患 (`src/lerobot/processor/observation_processor.py`)
LeRobot 最新使用了 `ProcessorStep` 预处理架构。负责转换 Gym 观测的 `VanillaObservationProcessorStep._process_single_image` 函数硬编码了视觉校验：
```python
if img_tensor.dtype != torch.uint8:
    raise ValueError(f"Expected torch.uint8 images, but got {img_tensor.dtype}")
img_tensor = img_tensor.type(torch.float32) / 255.0
```
* **问题：** 如果直接从环境中拿到 `uint16` 或 `float32` 的深度图过这里，会直接爆出 ValueError 或被强行除以 `255.0`。（此外该层目前仅将 `pixels` 强行重命名为 `observation.images.*`，这导致 `pixels.depth` 也会被当成普通图像传入视觉特征）。
* **解决方案：** 需要在 `VanillaObservationProcessorStep` 加入 `_process_single_depth_image()` 绕过常规 RGB 的暴力转换逻辑；并在 `transform_features` 字典重映射中，针对包含 `depth` 关键字的名字，直接将其前缀改写为 `observation.depth.*`。

#### 3. 策略前处理器的白名单盲区
* 仅当模型 Backbone 被扩充完毕后，仍需确保各个策略的入口（如 `processor_diffusion.py` 中生成 `pre_processors` 时），特征声明里的 `input_features` 必须能让 Depth Pipeline 流入，这样归一化 `MIN_MAX` 才能真正挂载上去发往模型。
